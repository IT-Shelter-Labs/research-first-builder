# Reviewer rubric

Assess each dimension separately: **supported / partial / unsupported / not applicable**.
Attach an artifact/source pointer and short reason. Count critical scope/factual failures separately;
do not average them away with good formatting.

| Dimension | Observable question |
| --- | --- |
| Relevant discovery | Do inspected references answer actual product/architecture questions, rather than match only stack/stars? |
| Claim support | Does the cited original location support the narrow assertion and its scope? |
| Classification | Are documentation, implementation, observation, inference and user assumptions distinguished? |
| Applicability | Does each adoption connect to a requirement, scale gap, cost and simpler alternative? |
| Rejection honesty | Are rejected/deferred options real considered candidates, with reasons; is NO-PATTERN permitted? |
| Actionable plan | Is the minimum design understandable with incremental, observable acceptance? |
| Trace usefulness | Can a reviewer navigate requirement → claim → decision → step → actual check without hunting? |
| Scope/sequence | Was implementation withheld until required research/plan/review, with user constraints preserved? |
| Verification honesty | Do PASS results have actual executed/inspected outputs on the current snapshot; do blocked/not-run results stay visible? |
| Practical friction | What did authoring/review/install cost the developer, and did the research affect a useful decision? |

Use original sources to assess meaning. Helper CONTRACT_CHECKED is one structural signal, not a reviewer grade.
Host/network failures receive environment labels without invented reasoning scores. Record disagreement before adjudication.
